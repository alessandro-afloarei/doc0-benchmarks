## Overview

fd is an ordinary cargo crate, `fd-find`, building one binary, `fd`, with Rust edition 2024 and a minimum supported Rust version of 1.90.0. Around cargo sit a `Makefile` for installing with completions and the man page, a GitHub Actions workflow that tests and packages fd for fourteen targets, and a release checklist with helper scripts.

Sources: [Cargo.toml:1-35](repo://Cargo.toml#L1-L35), [Makefile:1-52](repo://Makefile#L1-L52), [.github/workflows/CICD.yml:86-115](repo://.github/workflows/CICD.yml#L86-L115)

## Cargo features

| Feature | Default | Effect |
| --- | --- | --- |
| `completions` | yes | Pulls in `clap_complete` and enables `--gen-completions` |
| `use-jemalloc` | no | Uses `tikv-jemallocator` as the global allocator |
| `base` | no | Alias for `use-jemalloc` |

Sources: [Cargo.toml:94-98](repo://Cargo.toml#L94-L98), [src/main.rs:114-129](repo://src/main.rs#L114-L129)

jemalloc is used for speed, but it is only a dependency on targets where it works: not on Windows, Android, macOS, FreeBSD, OpenBSD, illumos, 32-bit musl or RISC-V 64. The same target list appears twice, as a `cfg` in `Cargo.toml` and as a `cfg` on the `#[global_allocator]` in `src/main.rs`, and the two must be kept in sync. On aarch64 Linux, `Cross.toml` passes `JEMALLOC_SYS_WITH_LG_PAGE=16` into cross builds, so a binary built there also runs on systems with 64 KiB pages.

Sources: [Cargo.toml:65-71](repo://Cargo.toml#L65-L71), [src/main.rs:38-54](repo://src/main.rs#L38-L54), [Cross.toml:1-6](repo://Cross.toml#L1-L6)

## Profiles and platform settings

The `release` profile enables LTO, strips symbols and uses one codegen unit, trading build time for a smaller, faster binary. `dev` keeps only line tables for fd and no debug info for dependencies, to speed up builds; the extra `debugging` profile inherits `dev` with full debug info. On Windows MSVC, `.cargo/config.toml` links the C runtime statically, so `fd.exe` needs no vcruntime DLL.

Sources: [Cargo.toml:79-92](repo://Cargo.toml#L79-L92), [.cargo/config.toml:1-8](repo://.cargo/config.toml#L1-L8)

## Makefile

`make` builds `target/release/fd` with `cargo build --profile release --locked`. `make completions` fills an `autocomplete` directory: bash, fish and PowerShell scripts are generated by the built binary with `--gen-completions`, while the zsh scripts and the `fdfind` variants are copied from `contrib/completion`. `make install` installs the binary, the completions and `doc/fd.1` under `prefix` (default `/usr/local`), honoring `DESTDIR`.

Sources: [Makefile:1-52](repo://Makefile#L1-L52)

## Continuous integration

### Checks

The `CICD` workflow runs on pull requests, pushes to `master` and tags. Its first jobs read the crate metadata (version, maintainer, MSRV) with `cargo metadata`, check formatting with `cargo fmt -- --check`, run `cargo clippy --all-targets --all-features -- -Dwarnings`, and run clippy and the tests on the MSRV toolchain.

Sources: [.github/workflows/CICD.yml:1-84](repo://.github/workflows/CICD.yml#L1-L84)

### Build matrix

The `build` job covers Linux (gnu and musl on x86_64, i686, aarch64 and arm), macOS (Intel and Apple Silicon) and Windows (MSVC on x86_64, i686 and aarch64, and GNU on x86_64). Linux targets are built with `cross`. Each target is built with `--release --locked` and tested; on `arm-*` and `aarch64-*` targets only the binary's own tests run (`--bin=fd`).

Sources: [.github/workflows/CICD.yml:86-115](repo://.github/workflows/CICD.yml#L86-L115), [.github/workflows/CICD.yml:160-198](repo://.github/workflows/CICD.yml#L160-L198)

### Packages

After the tests, the job runs `make completions` and packs an archive named `fd-v<version>-<target>`, `.zip` on Windows and `.tar.gz` elsewhere, holding the binary, README, licenses, changelog, man page and `autocomplete` directory. On Ubuntu runners it also builds a Debian package with `scripts/create-deb.sh`. For a `v*` tag it attests the artifacts, uploads them to the GitHub release, and a final job submits the MSVC zip files to Winget.

Sources: [.github/workflows/CICD.yml:200-256](repo://.github/workflows/CICD.yml#L200-L256), [.github/workflows/CICD.yml:274-309](repo://.github/workflows/CICD.yml#L274-L309)

`create-deb.sh` names the package `fd`, or `fd-musl` for musl targets, each conflicting with the other and with Debian's own `fd-find`. It installs the binary as `/usr/bin/fd`, the gzipped man page, the completions and the docs, adds an `fdfind` link with its own completions so both names work, and builds the package with `fakeroot dpkg-deb --build`.

Sources: [scripts/create-deb.sh:1-51](repo://scripts/create-deb.sh#L1-L51), [scripts/create-deb.sh:60-65](repo://scripts/create-deb.sh#L60-L65), [scripts/create-deb.sh:127-135](repo://scripts/create-deb.sh#L127-L135)

## Releasing

### Steps

`doc/release-checklist.md` is the procedure, meant to be pasted into the release pull request.

Sources: [doc/release-checklist.md:1-4](repo://doc/release-checklist.md#L1-L4)

1. Version bump: `scripts/version-bump.sh <version>` creates a `release-<version>` branch, sets the version in `Cargo.toml`, copies the MSRV into the README's install note, and renames the changelog's "Upcoming release" heading. Then run `cargo build` so `Cargo.lock` follows.
2. Pre-release: install the new build with `cargo install --locked -f --path .`, review `-h`, `--help` and the man page, refresh the README's help block, wait for CI, and run `cargo publish --dry-run`.
3. Release: merge the branch, push a `vX.Y.Z` tag (this starts the deployment), create the GitHub release with the changelog section as notes, check that archives and Debian packages appear, and `cargo publish` from a clean clone.
4. Post-release: add a new "Upcoming release" section with Features, Bugfixes, Changes and Other subsections at the top of `CHANGELOG.md`.

Sources: [doc/release-checklist.md:1-69](repo://doc/release-checklist.md#L1-L69), [scripts/version-bump.sh:1-21](repo://scripts/version-bump.sh#L1-L21)

### Updating the README help

`scripts/update-help.awk` rewrites the fenced block after the "Command-line options" heading in the README with the output of `cargo run --release --quiet -- -h`, starting at the `Usage` line, and fails if the command fails. Run it with `gawk -i inplace -f scripts/update-help.awk README.md`.

Sources: [scripts/update-help.awk:1-41](repo://scripts/update-help.awk#L1-L41), [doc/release-checklist.md:26-27](repo://doc/release-checklist.md#L26-L27)

## Contributing changes

Open an issue before a pull request so the change can be discussed. A change that alters fd's behavior needs an entry in the matching subsection of "Upcoming release" in `CHANGELOG.md`, in the form `- Short description, see #123 (@user)`. Code must build and pass the tests, and any use of AI tools must be disclosed. Tests are described in [[Testing]].

Sources: [CONTRIBUTING.md:1-46](repo://CONTRIBUTING.md#L1-L46)
