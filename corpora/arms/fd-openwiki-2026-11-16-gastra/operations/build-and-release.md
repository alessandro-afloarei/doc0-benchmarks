# Building, packaging, and releasing fd

The Cargo package is `fd-find`; its executable is `fd`, rooted at `src/main.rs`. This checkout declares version 10.4.2, edition 2024, and Rust 1.90.0 as its minimum supported toolchain. Treat `Cargo.toml` as authoritative when these values change. [Manifest](../../Cargo.toml#L15-L31).

## Build and run locally

From the repository root:

```sh
cargo build --locked
cargo run --locked -- -e rs . src
cargo test --locked
cargo build --locked --release
```

The ordinary executable is `target/debug/fd`; the release executable is `target/release/fd` (with `.exe` on Windows). `cargo install --locked --path .` installs the local package. For an interactive debugging build, `cargo build --profile debugging` enables full debug information: normal development builds retain line tables, dependencies disable debug information, and the custom debugging profile inherits development settings while enabling full debug info. Release builds enable LTO, stripping, and one codegen unit. [Profiles](../../Cargo.toml#L79-L92), [repository development instructions](../../README.md#L734-L747).

## Features and target differences

| Feature | Effect |
| --- | --- |
| Default | Enables `completions`. |
| `completions` | Includes `clap_complete` and the completion-generation CLI path. |
| `use-jemalloc` | Enables the optional allocator dependency where its target conditions apply. |
| `base` | Enables `use-jemalloc`; it is not part of the current default set. |

Do not assume every build uses jemalloc. Both the dependency declaration and allocator declaration exclude Windows, Android, macOS, FreeBSD, OpenBSD, illumos, 32-bit musl, and riscv64. Keep those two target expressions aligned when changing allocator support. [Feature/dependency gates](../../Cargo.toml#L65-L98), [allocator selection](../../src/main.rs#L38-L54).

`.cargo/config.toml` requests static C runtime linkage for x86_64 and i686 MSVC targets. It does not currently define the same entry for aarch64 MSVC. `Cross.toml` supplies the jemalloc page-size environment setting for aarch64 GNU and musl Linux builds. [MSVC configuration](../../.cargo/config.toml), [cross configuration](../../Cross.toml).

## Completion and installation assets

`make completions` builds the configured executable and populates `autocomplete/`. Bash, Fish, and PowerShell completions are generated by the binary; Zsh and the `fdfind` companion files are copied from `contrib/completion`. Completion generation therefore needs a binary built with the `completions` feature. The runtime generator derives its command name from the invoked executable filename. [Make targets](../../Makefile#L1-L42), [runtime generation](../../src/main.rs#L114-L129).

For a reviewable staged installation:

```sh
make completions
make install DESTDIR=/tmp/fd-stage prefix=/usr
```

The Makefile exposes `PROFILE`, `prefix`, `bindir`, `datadir`, and `exe_name`. Its install target writes the binary to `$(bindir)/fd`, plus completion assets and `doc/fd.1`. `exe_name` changes selected completion/man destinations, not the executable basename. The checked-in `doc/fd.1` is a maintained source asset; it is copied by packaging rather than regenerated from Clap by these rules. [Install rules](../../Makefile#L44-L52).

## CI and artifacts

The `CICD` workflow runs for pull requests, master pushes, tag pushes, and manual dispatch. It extracts Cargo metadata, checks formatting and Clippy, and tests the minimum Rust version with all features. Its build matrix covers Linux GNU/musl, macOS, and Windows variants, using `cross` for configured Linux targets and Cargo otherwise. Builds use `--locked --release`. ARM and aarch64 test invocations select `--bin=fd`, which excludes the separate integration test target. [CI entry and checks](../../.github/workflows/CICD.yml#L1-L84), [matrix](../../.github/workflows/CICD.yml#L86-L162), [test selection](../../.github/workflows/CICD.yml#L182-L203).

Archives contain the binary, README, licenses, changelog, man page, and completions. Windows uses ZIP; other matrix targets use tar.gz. Ubuntu jobs also call `scripts/create-deb.sh`, which accepts target/version/binary-path settings, stages package files, includes an `fdfind` symlink and companion completions, and invokes `fakeroot dpkg-deb`. It requires generated completion assets beforehand. [Archive assembly](../../.github/workflows/CICD.yml#L205-L255), [Debian inputs/assets](../../scripts/create-deb.sh#L5-L65), [package build](../../scripts/create-deb.sh#L127-L135).

Artifacts are uploaded during CI. Attestation and GitHub release publication are conditional on a tag matching `refs/tags/v` followed by a digit. A separate Winget job depends on the build job and selects Windows MSVC ZIP installers on `v` tags. These describe configured automation, not a guarantee that a particular remote release has completed. [Publishing conditions](../../.github/workflows/CICD.yml#L257-L309).

## Release maintenance

Use [doc/release-checklist.md](../../doc/release-checklist.md) as the maintained procedure: update version metadata and the lockfile, reconcile README/help/man text and changelog, wait for CI, run a publish dry run, then tag/release and publish the crate from a clean repository. Afterwards restore an Upcoming release changelog section.

`scripts/version-bump.sh VERSION` performs only part of that work: it switches/resets a release branch and edits the manifest, README, and changelog. It does not build to refresh `Cargo.lock` or perform release validation. Inspect its output and complete the checklist. [Script](../../scripts/version-bump.sh#L3-L21), [checklist](../../doc/release-checklist.md#L6-L54).

For test selection and change validation, see [testing and extension](../testing/contributor-guide.md). For everyday usage, return to [quickstart](../quickstart.md); output compatibility is covered in [output and pipelines](../integrations/output-and-pipelines.md).
