# Security Model and Fuses

Electron applications load web content and run Node.js, so the framework has to decide, for each process, what that code can reach. Some of those decisions are fixed when the binary is built, and they are called **fuses**. Others are per-window **web preferences** that the app sets at runtime, with defaults chosen by Electron. This page covers both, plus the integrity checks and renderer warnings that back them up. For how the processes themselves are separated, see [Process Model and IPC](/openwiki/architecture/process-model-and-ipc.md).

## Build-time fuses

Fuses are one-byte switches compiled into the binary. They are defined in `build/fuses/fuses.json5` and generated by `build/fuses/build.py`, which the `electron_fuses` action in `BUILD.gn` (around line 393) runs to write `fuses.h` and `fuses.cc` into the generated directory.

The generator reads the JSON, drops the comment and schema keys, and writes one `Is<Name>Enabled()` accessor per fuse. The fuse states are stored as a byte array named `kFuseWire`. The array starts with a sentinel string, then a version byte, a length byte, and one byte per fuse, where `'1'` means on and `'0'` means off. Each accessor reads its own byte. The sentinel makes the wire identifiable in the compiled data. The generator rejects a schema version of 256 or above, since the version has to fit in one byte.

In DCHECK-enabled builds the accessor first checks for a command-line switch named `--set-fuse-<name>` and uses its value (`1` for on) if present. Release builds ignore that switch.

The schema has rules that matter for compatibility. The `_comment` in `fuses.json5` says the schema version must be incremented for any breaking change, and that a fuse must never be removed or have its meaning changed. A retired fuse is marked `r`. These rules keep older binaries and their tooling compatible with newer fuse layouts.

The current fuse set and defaults are:

| Fuse | Default | Effect in this repository |
| --- | --- | --- |
| `run_as_node` | `1` (on) | Gates `ELECTRON_RUN_AS_NODE`. The Linux and macOS entry points check it before running `NodeMain`. |
| `node_options` | `1` (on) | Gates whether `NODE_OPTIONS` is honored. `shell/common/node_bindings.cc` checks it in two places. |
| `node_cli_inspect` | `1` (on) | Read in two places in `shell/`. The exact sites are not described further here. |
| `cookie_encryption` | `0` (off) | Read in two places in the browser network-context setup (`shell/browser/net/network_context_service.cc` and `system_network_context_manager.cc`). |
| `embedded_asar_integrity_validation` | `0` (off) | Enables ASAR header and V8 snapshot integrity checks, described below. |
| `only_load_app_from_asar` | `0` (off) | When on, `node_bindings.cc` restricts the app search paths to ASAR archives. |
| `load_browser_process_specific_v8_snapshot` | `0` (off) | Selects a browser-process-specific V8 snapshot. |
| `grant_file_protocol_extra_privileges` | `1` (on) | In `shell/renderer/renderer_client_base.cc`, lets the `file:` scheme register for service workers and the fetch API. |

Fuse defaults are a build input, so changing one in `fuses.json5` changes every binary built after it.

## Runtime defaults that set isolation

Web preferences, documented in `docs/api/structures/web-preferences.md`, control how each window's renderer is isolated. The defaults that matter most are:

- `contextIsolation` defaults to `true`. The preload script runs in a separate JavaScript context with its own globals, and the Electron APIs are visible only to that preload context, not to the loaded page.
- `sandbox` is documented as an option that places the renderer in the Chromium OS-level sandbox and disables the Node.js engine in that renderer. Preload code then receives a more limited environment.
- `nodeIntegration` defaults to `false`. When it is on, Node.js APIs are available in the page.
- `webSecurity` defaults to on. Turning it off also turns on `allowRunningInsecureContent` unless that option is set explicitly.

The option name is defined as a constant (`kContextIsolation`) in `shell/common/options_switches.h`. `shell/common/node_bindings.cc` contains comments and branches that handle renderers running with context isolation enabled, which keeps Node's environment setup consistent with that choice.

A renderer created with `sandbox: true` loads `lib/sandboxed_renderer/init.ts`, which is a restricted bundle. It fetches its preload scripts and process properties from the browser process with a synchronous `BROWSER_SANDBOX_LOAD` request. Its module maps are limited to `electron` and a few built-ins, as described in [Process Model and IPC](/openwiki/architecture/process-model-and-ipc.md). `lib/sandboxed_renderer/preload.ts` builds the process object passed to preload code (`createPreloadProcessObject`), so preload code sees only the properties that Electron chooses to expose. The browser side answers those requests in `lib/browser/rpc-server.ts`.

## ASAR integrity

When `embedded_asar_integrity_validation` is on, two checks apply on macOS and Windows:

1. `shell/common/asar/archive.cc` validates the ASAR header's signature when the archive has a relative path. It then reads the per-file block hashes from the integrity payload recorded in the header. If the header's integrity cannot be obtained for such an archive, the code calls `LOG(FATAL)`.
2. `ValidateV8Snapshot` in `shell/app/electron_main_delegate.cc` hashes the embedded V8 snapshot with SHA-256 and compares it to a generated constant (`snapshot_checksum::kChecksum`). The `CHECK` in that function aborts startup on a mismatch.

## File-protocol privileges

`grant_file_protocol_extra_privileges` controls whether the `file:` scheme may act like a web origin for service workers and the fetch API. `shell/renderer/renderer_client_base.cc` registers those capabilities only when the fuse is on, and it is on by default. Turning it off reduces what local files can do, at the cost of compatibility for apps that rely on service workers over `file:`.

## Renderer security warnings

`lib/renderer/security-warnings.ts` logs console warnings about insecure settings. `securityWarnings(nodeIntegration)` is called from `lib/renderer/common-init.ts` (around line 47), and it registers a `load` handler so that warnings are generated after the page loads. The handler logs only when `shouldLogSecurityWarnings()` returns true. That function is off unless the process's executable is the default Electron binary (`electron` on Linux, `electron.exe` on Windows, or the `Electron.app` bundle on macOS), and the environment variables `ELECTRON_ENABLE_SECURITY_WARNINGS` and `ELECTRON_DISABLE_SECURITY_WARNINGS` can override that default. Packaged apps therefore do not show these warnings unless they opt in.

The warnings cover Node.js integration with remote content (skipped for localhost), disabled `webSecurity`, insecure resources, `allowRunningInsecureContent`, `experimentalFeatures`, extra `enableBlinkFeatures`, missing or insecure Content-Security-Policy, and allowed popups. They are advisory. They do not change behavior.

## Invariants and failure behavior

- In release builds a fuse's value is fixed when the binary is built, and no runtime API changes it. DCHECK-enabled builds also accept the `--set-fuse-<name>` switch as an override.
- The web-preference defaults in `docs/api/structures/web-preferences.md` are the baseline. Apps that turn on `nodeIntegration`, turn off `contextIsolation`, or turn off `webSecurity` take those risks explicitly.
- With `embedded_asar_integrity_validation` on, a failed ASAR header check or snapshot checksum stops startup rather than loading the modified code.
- Security warnings are advisory and are suppressed for packaged apps by default.
