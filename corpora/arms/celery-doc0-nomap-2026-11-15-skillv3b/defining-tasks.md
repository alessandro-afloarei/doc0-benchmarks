## Overview

A task is a class derived from `celery.app.task.Task` with exactly one instance per app, registered under a name. Most tasks are written as functions and turned into classes by `@app.task`; the class attributes then decide how the task is sent, retried, acknowledged and recorded. This page covers how a task is built, the attributes and hooks you can set, and the ways a running task controls its own outcome (`retry`, `replace`, `update_state`). Sending is covered on [[Calling Tasks and the Message Protocol]] and the worker-side execution on [[Task Tracing and Execution]].

Sources: [celery/app/task.py:206-216](repo://celery/app/task.py#L206-L216), [celery/app/base.py:590-633](repo://celery/app/base.py#L590-L633)

## From function to task class

### Building the class

`@app.task(**options)` hands the function and its options to `_task_from_fun`, lazily through a `PromiseProxy` until the app is finalized ([[The Celery Application]] describes that step). `_task_from_fun` builds a new class with `type(fun.__name__, (base,), attrs)` where `base` is the `base=` option or the app's `Task` class, and `attrs` holds the app, the name, the function as `run`, its docstring and module, a `__header__` signature checker, and every remaining option. Options such as `max_retries=5` or `acks_late=True` therefore become class attributes.

Sources: [celery/app/base.py:515-585](repo://celery/app/base.py#L515-L585), [celery/app/base.py:590-633](repo://celery/app/base.py#L590-L633)

The function becomes `run` as a `staticmethod`, unless `bind=True`, in which case it is a normal method and receives the task instance as `self`. A bound task can read `self.request`, call `self.retry()` and `self.update_state()`.

Sources: [celery/app/base.py:614-626](repo://celery/app/base.py#L614-L626)

```python
@app.task(bind=True, max_retries=5, default_retry_delay=30)
def fetch(self, url):
    try:
        return download(url)
    except ConnectionError as exc:
        raise self.retry(exc=exc)
```

Sources: [celery/app/task.py:756-790](repo://celery/app/task.py#L756-L790)

The name defaults to `module.function`. `gen_task_name` replaces `__main__` with `app.main` when the module is run as a script, so the worker and the client agree on names. Class-based tasks registered with `app.register_task` get the same treatment from their class name.

Sources: [celery/utils/imports.py:122-141](repo://celery/utils/imports.py#L122-L141), [celery/app/base.py:635-655](repo://celery/app/base.py#L635-L655)

### Argument checking

`__header__` is a function generated by `head_from_fun`: it has the task function's signature and an empty body, built with `exec` because calling a real function is much faster than `inspect.Signature.bind`. When `typing` is true (it defaults to the app's `strict_typing`), `apply_async` calls it with the arguments, so a wrong call raises `TypeError` in the caller instead of failing on the worker.

Sources: [celery/utils/functional.py:364-394](repo://celery/utils/functional.py#L364-L394), [celery/app/task.py:657-664](repo://celery/app/task.py#L657-L664)

### Pydantic arguments

With `pydantic=True`, `_task_from_fun` wraps the function in `pydantic_wrapper`. The wrapper binds the arguments to the signature, validates every argument annotated with a `BaseModel` subclass through `model_validate` (passing `celery_app` and `celery_task_name` in the validation context), and dumps a returned model with `model_dump(mode='json')` when it matches the return annotation. Callers can then send plain dicts and the task receives models. `pydantic_strict`, `pydantic_context` and `pydantic_dump_kwargs` tune the validation.

Sources: [celery/app/base.py:127-205](repo://celery/app/base.py#L127-L205), [celery/app/base.py:609-611](repo://celery/app/base.py#L609-L611)

## Binding and configuration defaults

### Settings copied at bind time

`Task.bind(app)` runs once per class when the task is registered or first used. It stores the app, sets `typing` from `strict_typing`, and for each pair in `from_config` copies the app setting into the attribute when the attribute is `None`. A `None` attribute means "use the app default", and a value set on the task wins.

Sources: [celery/app/task.py:399-457](repo://celery/app/task.py#L399-L457)

| Attribute | Setting it falls back to | Effect |
| --- | --- | --- |
| `serializer` | `task_serializer` | Serializer for arguments |
| `rate_limit` | `task_default_rate_limit` | Per-worker limit such as `'10/m'` |
| `priority` | `task_default_priority` | Message priority |
| `time_limit`, `soft_time_limit` | `task_time_limit`, `task_soft_time_limit` | Hard kill and `SoftTimeLimitExceeded` |
| `track_started` | `task_track_started` | Store a `STARTED` state |
| `acks_late` | `task_acks_late` | Acknowledge after the task runs |
| `acks_on_failure`, `acks_on_timeout` | `task_acks_on_failure`, `task_acks_on_timeout` | Late-ack behaviour on failure or timeout |
| `reject_on_worker_lost` | `task_reject_on_worker_lost` | Requeue when the child process dies |
| `ignore_result` | `task_ignore_result` | Do not store the return value |
| `store_errors_even_if_ignored` | `task_store_errors_even_if_ignored` | Store failures even when results are ignored |

Sources: [celery/app/task.py:398-414](repo://celery/app/task.py#L398-L414)

`acks_on_failure` and `acks_on_timeout` default to the deprecated `acks_on_failure_or_timeout`, and to `True` when that is unset. Other attributes have fixed defaults: `max_retries = 3`, `default_retry_delay = 180` seconds, `trail = True` (record child results), `send_events = True`, `throws = ()` (exceptions logged as expected rather than as errors), `expires`, and the `Strategy` and `Request` classes the worker uses.

Sources: [celery/app/task.py:216-262](repo://celery/app/task.py#L216-L262), [celery/app/task.py:315-372](repo://celery/app/task.py#L315-L372), [celery/app/task.py:432-443](repo://celery/app/task.py#L432-L443)

### Annotations

The `task_annotations` setting changes attributes of tasks you did not write. It accepts a dict keyed by task name (or `'*'` for all tasks), an object with an `annotate(task)` method, or a dotted name of such a class. On first bind, `annotate()` applies every match: plain keys set attributes, and keys starting with `@` wrap a method with `add_around`, which keeps the original as `__wrapped__`.

Sources: [celery/app/annotations.py:18-52](repo://celery/app/annotations.py#L18-L52), [celery/app/task.py:477-493](repo://celery/app/task.py#L477-L493)

```python
app.conf.task_annotations = {
    'tasks.add': {'rate_limit': '10/s'},
    '*': {'on_failure': my_on_failure},
}
```

Sources: [celery/app/annotations.py:18-31](repo://celery/app/annotations.py#L18-L31)

## The request context

Every execution pushes a `Context` on the task's thread-local `request_stack`; `task.request` returns the top one, or an empty default when the task is not running. The context carries what the worker read from the message: `id`, `args`, `kwargs`, `retries`, `eta`, `expires`, `group`, `group_index`, `chord`, `chain`, `callbacks`, `errbacks`, `root_id`, `parent_id`, `delivery_info`, `hostname`, `reply_to`, `timelimit`, `is_eager` and `called_directly`. Headers not used by Celery are kept in `request.headers`.

Sources: [celery/app/task.py:75-160](repo://celery/app/task.py#L75-L160), [celery/app/task.py:1234-1254](repo://celery/app/task.py#L1234-L1254)

Calling a task object directly (`add(2, 2)`) runs `run` in the current process through `__call__`, which pushes the task on the global task stack and a request with `called_directly` left true. `as_execution_options()` turns a request back into `apply_async` options, which is how retries and replacements keep the task's ids, group, chord and time limits; it drops RabbitMQ `x-death` headers so a retried message is not mistaken for a dead-letter cycle.

Sources: [celery/app/task.py:160-196](repo://celery/app/task.py#L160-L196), [celery/app/task.py:495-503](repo://celery/app/task.py#L495-L503)

## Retrying

### Manual retries with retry()

`self.retry()` computes the next attempt from the current request. It increments `retries`, builds a signature with `signature_from_request` (same id, same options, optional new arguments) and either raises `MaxRetriesExceededError` (or the `exc` you passed) when the limit is reached, or sends the signature with `countdown` defaulting to `default_retry_delay`. It then raises `Retry`, which the tracer records as the `RETRY` state rather than a failure.

Sources: [celery/app/task.py:813-867](repo://celery/app/task.py#L813-L867)

Three cases change that flow. A task called directly re-raises the original exception, because there is no message to resend. An eager task raises `Retry` carrying the signature, and `apply()` runs it again locally. A failure to publish the retry message raises `Reject(requeue=False)`, so the worker rejects the original message rather than losing it silently.

Sources: [celery/app/task.py:819-866](repo://celery/app/task.py#L819-L866), [celery/app/task.py:937-951](repo://celery/app/task.py#L937-L951)

### Automatic retries

`autoretry_for` saves you the `try`/`except`. `add_autoretry_behaviour` wraps `run` once (keeping the original as `_orig_run`) so that exceptions in `autoretry_for`, except those in `dont_autoretry_for`, `Ignore` and `Retry`, call `task.retry(exc=exc, **retry_kwargs)`. With `retry_backoff`, the countdown is `factor * 2 ** retries` capped by `retry_backoff_max` (600 seconds by default), and `retry_jitter` (on by default) picks a random value up to it to spread retries out.

Sources: [celery/app/autoretry.py:8-66](repo://celery/app/autoretry.py#L8-L66), [celery/utils/time.py:463-477](repo://celery/utils/time.py#L463-L477)

```python
@app.task(autoretry_for=(ConnectionError,), retry_backoff=2,
          retry_backoff_max=300, retry_kwargs={'max_retries': 8})
def sync(account_id):
    ...
```

Sources: [celery/app/autoretry.py:10-31](repo://celery/app/autoretry.py#L10-L31)

## Replacing and extending a running task

`self.replace(sig)` ends the current task and puts `sig` in its place under the same id, so results the caller already holds stay valid. It carries the task's callbacks and errbacks over to the new signature, turns a group into a chord ending in `celery.accumulate` so callbacks can be linked, freezes the signature with the current id, copies the chord, group and root ids, increments `replaced_task_nesting`, and appends the rest of the current chain. `on_replace` then sends it and raises `Ignore`, which tells the tracer not to store a result for the replaced task.

Sources: [celery/app/task.py:1029-1095](repo://celery/app/task.py#L1029-L1095), [celery/app/task.py:1211-1227](repo://celery/app/task.py#L1211-L1227)

`self.add_to_chord(sig)` adds a task to the chord the current task belongs to, by telling the backend to expect one more result; only the Redis backend supports it. `self.update_state(state=..., meta=...)` stores a custom state such as `PROGRESS` with metadata that `AsyncResult.info` returns to the caller.

Sources: [celery/app/task.py:1097-1133](repo://celery/app/task.py#L1097-L1133)

## Handler hooks

A custom base class can override hooks the worker calls around execution. Their return values are ignored; [[Task Tracing and Execution]] shows the order in which the tracer calls them and the signals sent around them.

Sources: [celery/app/task.py:1135-1150](repo://celery/app/task.py#L1135-L1150)

| Hook | When it runs |
| --- | --- |
| `before_start(task_id, args, kwargs)` | Before `run`, in the worker |
| `on_success(retval, task_id, args, kwargs)` | After `run` returns |
| `on_retry(exc, task_id, args, kwargs, einfo)` | After `retry` raised `Retry` |
| `on_failure(exc, task_id, args, kwargs, einfo)` | After `run` raised an exception |
| `after_return(status, retval, task_id, args, kwargs, einfo)` | After the outcome is stored, in every case |
| `on_replace(sig)` | When `replace` is called; must call the base implementation |
| `on_bound(app)` | Class method, when the class is bound to an app |

Sources: [celery/app/task.py:1135-1227](repo://celery/app/task.py#L1135-L1227), [celery/app/task.py:457-465](repo://celery/app/task.py#L457-L465)

```python
class DatabaseTask(app.Task):
    def on_failure(self, exc, task_id, args, kwargs, einfo):
        alert_ops(task_id, exc)

@app.task(base=DatabaseTask)
def import_rows(path):
    ...
```

Sources: [celery/app/base.py:590-605](repo://celery/app/base.py#L590-L605)

## Running a task locally

`task.apply()` runs the task in the calling process and returns an `EagerResult`. It builds a request dict with `is_eager=True`, the parent and root ids of any task already running, and the task's time limits, then calls a tracer from `build_tracer(..., eager=True)`. Exceptions propagate when `throw` or `task_eager_propagates` is set. `task_always_eager` makes `apply_async` serialize and deserialize the arguments (to catch values the serializer cannot handle) and call `apply`; [[Testing Celery Applications]] explains when that is useful.

Sources: [celery/app/task.py:869-951](repo://celery/app/task.py#L869-L951), [celery/app/task.py:677-698](repo://celery/app/task.py#L677-L698)

## Pickling tasks

A task instance pickles to its name and module only. On the other side `_unpickle_task_v2` imports the module if needed and takes the task from the current app's registry, so a task can be passed as an argument without shipping its class.

Sources: [celery/app/task.py:506-514](repo://celery/app/task.py#L506-L514), [celery/app/registry.py:61-68](repo://celery/app/registry.py#L61-L68)
